# Advisory MSVC hash checks for contributor pull requests

Task p124, 2026-11-14. Engineer: gpt-6.1-sol; human owner: awarebayes. Exposure: public
reconstruction source and sanitized accepted records only; no private game input was used to
implement this prototype. Build identity is the pinned `sse-steam-1-7-104` manifest in
`builds/target.json`. This document is a tooling design, not a behavior or clean-room claim.

## Phase 1: prove the compiler with existing public records

Dispatch `.github/workflows/ci-hash-check.yml` on main. The `windows-2022` job asks the runner's
Visual Studio installer to add `Microsoft.VisualStudio.Component.VC.v141.x86.x64` and the pinned
SDK headers. `tools/ci_msvc_install.ps1` records installation wall time. `tools/ci_hash_check.py
probe` prints the compiler version, size and SHA-256, plus the hashes and sizes of `c1xx.dll`,
`c2.dll` and `link.exe`. `MATCH` requires x64 version 19.16.27054 and every hash in
`tools/verifier/pinned.sha256`; a v141 label alone proves nothing.

If the installed component differs or the self-test fails, the job tries Microsoft's evergreen
VS2017 Build Tools bootstrapper at `https://aka.ms/vs/15/release/vs_buildtools.exe`. It checks
the bootstrapper's Microsoft Authenticode signature and supplies the existing fixed 15.9.85
catalog URL and SHA-256 from `tools/verifier/setup_boat_machine.sh` through
`--installCatalogUri`. It probes the resulting binaries against exactly the same pins. This
tests an official exact-version source without assuming that the evergreen installer or a
toolset directory name will yield the pin. Failure or mismatch remains visible; no pin changes.

The public self-test compiles three separate units twice, with the flags read from the accepted
record's recipe, the verifier's cleared environment and include-closure checks, and a 180-second
compile timeout. It compares these functions with their existing public records:

- `NiTimeController::ProcessClone`, RVA `0xef8900`, 53 bytes, the contributor setup self-test.
- `NiAVObject::GetCollisionObject` (const), RVA `0x405a50`, 33 bytes.
- `TESForm::GetGoldValue`, RVA `0x1f3560`, 157 bytes.

The expected values come from the accepted records, checked for source-digest, recipe and
cross-run agreement, rather than newly published target data. Extraction calls the unchanged
comparator's `find_function` and `check_relocation_layout`; hashing calls its
`code_section_sha256` directly. These three references have one code section and no funclet
sections. Phase 1 tests clean-compilation determinism on these units, not all C++ features.

**Existing hash semantics:** `code-section-sha256-v1` hashes section names, lengths, bytes and
relocation offset/type/target identity. It excludes object timestamps, symbol indices and debug
paths. It does not simply zero relocation fields. Phase 1 reproduces this existing public hash;
it does not pretend it is the future masked-target hash below. Neither comparison runs the
game comparator against a target image on CI.

Compiler packages, objects and raw compiler diagnostics stay in runner scratch and are never
uploaded as artifacts. No `actions/cache` toolset cache is enabled: `LEGAL.md` prohibits
distributing compiler packages through this project, and GitHub caches can be restored by fork
pull requests. An installation also has installer state outside the toolset directory, so
restoring that directory alone would not prove a valid installed component. Report the uncached
installation time from logs; cached time is **not measured**, not an invented speedup. Revisit
caching only with a distribution basis and a reproducible installation strategy.

## Phase 2: proposed target manifest, not generated by this task

There is **no function-size threshold**. The maintainer explicitly allowed target hashes for
all functions, having weighed that very small functions' hashes can be brute-forced back to
their bytes, and most small functions are already matched with hashes already public. The
verbatim decisions are beside the G4 note in `docs/authorizations.md`.

Generating and publishing hashes for unmatched functions remains a separate step **after Phase 1
proves the toolchain**. The orchestrator confirms before publication. No unmatched-target hashes,
manifest generator or PR compile job are implemented here.

The proposed JSON manifest has a versioned schema and hash method; target build id and image
SHA-256; recipe, compiler pin and comparator source digests; and a `functions` list. Each member
binds `(build_id, rva, size)`, a candidate symbol binding where known, `normalized_sha256` and
`masked_offsets`. The last field is a sorted list of non-overlapping `{offset, width,
relocation_type}` fields relative to the function start. It must be fixed by trusted main data,
never chosen or expanded by the PR. Unknown bindings remain unknown and yield `not-covered`.

For the first hash-method version, normalization means extracting the exact comparator-delimited
function range, preserving instruction order, registers and every unmasked byte, and replacing
each published relocation field with zero bytes. Hash the resulting full-length buffer with
SHA-256; do not delete masked bytes. The candidate must have the exact size and the same
relocation field offsets, widths and supported types. Reuse `check_relocation_layout` and the
comparator's supported-relocation rules (currently four-byte fields), rejecting overlaps,
out-of-range or unsupported fields. Both sides apply the same fixed mask. No branch, immediate,
padding or register normalization is implied. This is a deliberately weaker byte pre-filter:
masked fields omit reference targets and addends; the real comparator resolves and checks them.

Future generation happens locally, against the owner's hash-checked pinned image, with a pinned
comparator and recipe. Establish function boundaries and relocation/reference masks from reviewed
local evidence, record the extraction revision and method, and retain bytes and diagnostics
locally. An unmatched function's mask may be unknown without a candidate: report `not-covered`
until justified; do not infer zero fields or publish guessed masks as facts. Only hashes, masks
and reviewed metadata may leave the machine. Validate identities, ranges, masks and input digests
locally, reproduce the extraction, then obtain the orchestrator's publication confirmation.
This describes the procedure only; there is no command here that generates or publishes it.

## Proposed PR job and p123 integration

Use `pull_request`, a GitHub-hosted disposable Windows runner, `contents: read`, no secrets,
no environment credentials, no OIDC, no private inputs and no execution of resulting objects.
Check out main at a recorded immutable SHA with `persist-credentials: false`. Run only that
revision's tools, recipes and manifest. Fetch the PR head by its event SHA as git objects and
read only allowed `reconstruction/<area>/<Class>.{h,cpp}` source blobs as data. Never check out
or import the PR's tools, run build systems, hooks, submodules, response files or PR commands.

Run main's contributor intake first (scope, 64 KiB file cap, text, symlink and source lint).
Materialize the approved source blobs over a separate scratch copy of main's reconstruction
tree, with no links or path escapes. Use main's include-closure scan, cleared environment,
fixed include roots and `/showIncludes` equality checks before hashing. Bound compiler time
and job time; compiler diagnostics remain scratch-only because source can steer their contents.
Compile-only input still exposes the old compiler parser to hostile C++, so the disposable job
has no valuable credentials or private game data. No toolset/object/diagnostic cache or artifact.

A `pull_request` workflow itself can be changed by the PR. Fetching main's scripts does not
authenticate a malicious replacement workflow. Task p123's `tools/contrib_autopilot.py` must
therefore treat this result only as advisory, bind it to the exact head SHA and trusted main
tools/manifest/toolchain digests, and repeat authoritative intake locally before confirmation.
Do not use `pull_request_target` to give PR compilation elevated access.

The proposed sanitized machine result reports `toolset` (`MATCH`, `MISMATCH`, `ERROR`), per-function
`hash-equal`, `hash-different`, `not-covered` or `compile-failed`, all input revisions and
`acceptance: not-evaluated`. An absent or stale manifest, wrong compiler, unsupported layout or
missing binding is not a pass. Hash equality can prioritize the p123 queue; a difference can
give contributors early feedback. Neither writes inventory state nor accepts/rejects a function
on behalf of the acceptance pipeline.

The two independent verifier hosts, different OS loaders, complete comparator checks, Reviewer
approval and integrated-source checks in `docs/verification.md` remain mandatory. CI does not
check reference identity, unwind/EH scope, aliases, layout completeness or provenance. Counting
GitHub Actions as an acceptance host would require a separate acceptance-rule change.

## Sources and limits

Microsoft documents the [v141 component](https://learn.microsoft.com/en-us/visualstudio/install/workload-component-id-vs-build-tools?view=vs-2022)
and the [installer parameters](https://learn.microsoft.com/en-us/visualstudio/install/use-command-line-parameters-to-install-visual-studio),
including catalog selection. The existing pinned catalog is the exact-source candidate tested
here; the [VS2017 release history](https://learn.microsoft.com/en-us/visualstudio/releases/2017/vs2017-relnotes-history)
does not by itself prove binary identity. GitHub documents [cache visibility and scope](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching).
These are public documentation sources consulted on 2026-11-14; successful installation and
binary identity must be measured in the actual workflow run. The private handoff records the
pushed revision, run URL, observed results and remaining limits.
