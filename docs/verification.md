# Verification and honest progress

## Bootstrap gate

`data/progress.json` is the sole public progress input. `tools/check.py` validates it and
`tools/build_site.py` derives all headline totals. A function may be `matched` only when its
inventory entry names a match record under `reports/` and has a Reviewer record beside it, both
of which `tools/check.py` accepts (the "Match gate" section below). A status flip, a
`success: true` flag or a hand-written report is rejected. Weakening the gate is a machinery
change under the acceptance rule below, made to this file, `tools/check.py`,
`tests/test_match_gate.py` and `tests/test_accept_function.py` together.

The function inventory holds individually selected entries only, and scope totals are unknown
(`null`). No overall percentage is shown until a reviewed inventory defines scope and
exclusions. Task completion, type coverage, behavioral validation and byte-match coverage must
never be combined into one completion score. The function states are `mapped`, `analyzed`,
`reconstructed` and `matched`. All are mutually exclusive current states, not cumulative counts.
A reconstruction is not a match.

## Requirements for a future accepted match

- A pinned executable hash/store/version/architecture and stable function RVA + length.
- A reproducible source revision, source path and recipe, exact compiler binary hash,
  SDK/library provenance, command flags and tool versions.
- All function bytes covered, including exception-related code in the selected scope (the scope
  comparator contract version 2 defines in `docs/comparator-contract.md`);
  calls, data references, relocations and alias/fold handling checked rather than masked away.
- Explicit definitions for generated code, linked libraries, thunks, padding, excluded entries
  and overlapping function ranges. No silent scope shrinkage to improve a percentage.
- A local report generated by the comparator; public form contains metadata, hashes and results,
  no bytes or disassembly. Include report schema/comparator version and reproduction command.
- An independent re-check against the pinned source and target, and acceptance under the rule
  below. Claims accepted into the report must refer to integrated source, not merely an unmerged
  agent submission.

## Acceptance rule

Acceptance of a function as `matched` is automated. The maintainer decided that individual
functions are not hand-reviewed at this target's scale; do not ask the maintainer to review or
accept individual functions or batches. Acceptance has two tiers (maintainer decision,
`docs/authorizations.md`): tier 1, `matched`, rests on comparator evidence and basic hygiene and
is the only tier that counts as a match; tier 2, `named`, says the names and their origin labels
are also clean. Tier 2 never blocks tier 1 and is improved afterwards, mostly by tooling.

### Tier 1: `matched` (blocking)

A function is accepted only when ALL of these hold:

1. **Deterministic evidence.** A comparator pass with complete coverage of the function on the
   pinned image, built from the pinned source revision, recipe and compiler; the same pass
   reproduced on a second verifier host; and the validator's report/source consistency checks
   passing on the integrated tree ("Match gate" below). Only this is evidence of a byte match.
   A model's opinion, including the Reviewer's, never is.
2. **Automated hygiene**, enforced by tools, not by a Reviewer:
   - `tools/lint_reconstruction.py` reports nothing for any file under `reconstruction/` (run
     by `tools/check.py`): no inline assembly, `__emit`, raw byte arrays, `\x` byte strings,
     codegen-only pragmas or `__declspec`; header fields present; include style. `__forceinline`,
     `noinline`, `[[msvc::...]]` attributes and codegen intrinsics (`INTRINSICS` there) each
     carry a justification comment on the same or the previous line. A file holding a
     `COMMUNITY(..., GPL...)` label (or LGPL, AGPL, in any case) names GPL in its leading
     comment, as `docs/authorizations.md` requires, and every `COMMUNITY(` (any case,
     any file) is a well-formed label, and a label for a known community repository (owner and
     repository compared without case) spells it as listed and states its licence
     (`COMMUNITY_LICENCES` in the lint). An MIT licence notice is never cut short or edited.
     A `SIBLING(...)` label,
     in any file, or a `Sibling source:` line names only an allowed sibling at its pin with its
     licence word, and a `Sibling source:` line sits in the leading comment with no `..` in its
     path; `tools/check_labels.py` (private clone) checks the cited path and
     line. Whether a body was reused at all is not machine-checked; that is the Reviewer's.
   - The unit compiles from tracked files only: the match record's translation unit is the
     include closure of repository files, and `tools/check.py --staged` (the pre-commit check)
     recomputes it from the index, so a closure file that is not staged fails the commit.
   - What the tools cannot see is left to the Reviewer's blocking grounds below: a helper
     introduced only for matching, or a justification comment that is not a programmer's reason.
3. **Reviewer approval.** A Reviewer (`docs/reviewer-runbook.md`; in Claude Code the
   `.claude/agents/reviewer.md` subagent) of an admitted class, started with fresh context, which
   did not draft, engineer or triage that function, returns `approve` for it (or supplies the family approval
   and member reviews under "Family reviews" below),
   for the current source or, under "Label-only re-acceptance" below, for an earlier source whose
   compiled code section is identical. The Reviewer is a necessary sanity and provenance check,
   not match evidence: it can only veto or approve, cannot substitute for item 1, and cannot edit
   the reviewed source, the comparator, the validator or any report. Its **blocking grounds**,
   the only reasons for `reject`, are:
   - the source is pasted or lightly edited decompiler output (tells: `undefined8`, `param_1`,
     `local_28`, `FUN_`/`DAT_` names, decompiler casts and control-flow shapes);
   - byte steering: contortions with no programmer-level reason, such as nonsensical control
     flow, dead code, a helper, attribute or intrinsic whose only plausible reason is forcing
     bytes (a lint-required justification that is not a reason a programmer had counts here);
   - code that cannot be what it claims, such as an unreachable branch or impossible type use
     that signals a wrong binding or a wrong class;
   - provenance: code from unlicensed projects other than the FNV decompilation
     `momusdigital/fnv_decomp@91e1b6e8`, which the maintainer allowed (`docs/authorizations.md`,
     Notes); leaked or proprietary material; a source header that does not state provenance and
     source exposure, or whose origin or licence statement is false; and undeclared reuse of
     sibling code, meaning a unit that reuses an FNV body or a substantial part of one without a
     `Sibling source: <repo>@<rev> <path>[:<line>]` header line. FNV material is never evidence
     for the match claim;
   - claim scope beyond a byte match of the checked code (a claim of behaviour, or of a name
     being right);
   - publication hygiene per `PROVENANCE.md` and `LEGAL.md`;
   - a match record that does not bind the unit (digest, recipe, compiler or image disagree, or
     the second-host run is missing).

   Not blocking: names, name-origin labels (missing, unlabelled community names, `GUESS` where a
   community or sibling name exists, a missing or imperfect `SIBLING(...)` label on a name or
   declaration taken from FNV; a reused body is declared by its `Sibling source:` line, whose
   absence is the blocking ground above), placeholder versus community naming, dead or
   leftover declarations that compile to nothing, header and comment wording, and missing notes.
   The Reviewer lists these as `naming_findings` for the function and still approves if no blocking ground holds.
   They are published (next item), so they hold no code, bytes, disassembly or private paths.

   **Admitted Reviewer classes.** The Opus class is admitted. The Terra class as the Reviewer
   is admitted only as `gpt-6.1-terra` under the `claude-low` profile, through the maintainer's
   Codex subscription and within the exposure in `docs/authorizations.md`. Its blind calibration
   against Opus at revision `2209f4b` covered 67 functions: 60 agreed, 7 were stricter, none
   were laxer and all 4 reference rejects were caught. The reviews were
   `.local/reviews/review-p26-terra-cal-{1..4}.md` and
   `.local/reviews/review-p19-wave2-{1..4}.md`. This was one wave at one revision, mostly small
   functions, with only 4 reference rejects. Sonnet is prepared, pending blind calibration and a
   Reviewer-checked rule change.

   The Sol class as the strong Reviewer is admitted only as `gpt-6.1-sol` under `claude-low`
   for any review. Terra is the default first Reviewer. For the strong duties (sampling second
   passes, confirmation of a non-Opus `escalate` before the maintainer, and reviews of comparator,
   validator, verifier or acceptance-rule changes) the tools admit Sol or Opus, never Terra, and
   require a different model from the first review. Unlike Terra,
   Sol was admitted by maintainer decision WITHOUT a calibration:
   "sol is goood enough dont waste time" (`docs/authorizations.md`, Notes). Sol may give a fresh
   function review when confirming an escalation. Under `claude-low`, every second pass must use a different model from the first review (Opus
   aliases count as one model); if the first review was Sol, use an independent Opus Reviewer.
   Outside `claude-low`, Opus remains required for these strong review duties and the existing
   sampling policy is unchanged. Reviewer independence is per run: use fresh context, never the
   run that drafted, engineered, triaged or first-reviewed the function, including machinery
   and rule changes. A non-Opus `reject` needs no confirmation.
   A new Reviewer model or class counts as a new Reviewer version for sampling. The acceptance
   and flow tools refuse models not admitted for the profile in use.

   Verdicts are `approve`, `reject` (on a blocking ground, back to the Drafter or Engineer with
   reasons) or `escalate` (with a category: `provenance`, `legal`, `systemic` or `other`). The
   review is kept privately at `.local/reviews/<task-id>.md`; a sanitized verdict record
   (reviewer model, verdict, escalation category, review file SHA-256, date, the function
   identity and source digest it reviewed, and the naming findings) goes alongside the public
   report as `reports/<build id>/<rva>.review.json`.
4. **Integration.** An Engineer merges the passing branch, reruns the full checks and the
   verifier on the integrated tree, and records the acceptance with `tools/accept_function.py`,
   which writes the verdict record and sets that entry to `matched` only if the validator
   accepts the result. The change is then committed and pushed by the integrating Engineer (or
   the orchestrator when run with a shell) after the pre-push checks in `AGENTS.md`.

Reviewer passes need G2, since they read reconstructed source. A `reject` or `escalate` stops
acceptance of that function until a later Reviewer pass on a revised source returns `approve`;
`tools/accept_function.py` never accepts a `reject`, whatever its reasons say. A reject given
under the earlier rule for naming reasons only is cleared by a fresh Reviewer pass under this one,
not by editing the review.

### Tier 2: `named` (non-blocking)

Tier 2 is per function, because status, records and naming findings are per function; its
label check runs on the function's whole translation unit, since labels live in the unit's
files. A `matched` function is `named` when its Reviewer record lists no open naming finding
(an empty `naming_findings`, schema 3) and `tools/check_labels.py` reports nothing for every file
of its unit, each of which declares `Labels: v2`. It is the field `named` (`true` or `false`)
beside `status` in `data/progress.json`, set only by `tools/accept_function.py` (on every
acceptance and with `--refresh-named`); absent means not assessed. It is not a status value, so
the `matched` counts are unaffected; `reconstruction/INDEX.md`, the progress picture and the
site show it separately.

What enforces it: `tools/check.py` refuses `named` on an entry that is not `matched`, a
non-boolean value, and `named: true` unless the entry's Reviewer record is schema 3 with an empty
`naming_findings`. The label check needs the private community checkouts under `.local/`, which
CI lacks, so `tools/check.py` cannot re-run it: that half is checked by `tools/accept_function.py`
when it sets the field (no checkout, or any finding, gives `false`), and it holds for the unit
digest the Reviewer record binds, since any edit to the unit makes the acceptance stale and the
next acceptance recomputes the field. A new rule in `tools/check_labels.py` is applied to
accepted functions by `--refresh-named`. Functions accepted before this rule have no
`naming_findings` (schema 1 or 2 records) and stay unassessed until a later review.

Open naming findings are closed by a Reviewer: a later full or delta review that lists none.
Label fixes themselves do not need one: see "Label-only re-acceptance".

**Sampling safeguard.** At least 5% of individually reviewed accepted functions (including reviewed
family members), chosen at random by the orchestrator,
plus the first 20 accepted functions under every new recipe or compiler, every new Drafter prompt
version, every new Reviewer prompt version (`.claude/agents/reviewer.md`, `docs/reviewer-runbook.md`)
or Reviewer model, and every new version of
the acceptance rule (this section and `tools/accept_function.py`), and the first 20 label-only
re-acceptances under each acceptance-rule version, get a second independent Reviewer pass (fresh context, a different
Reviewer run, Opus class outside `claude-low`; under `claude-low`, an admitted strong Reviewer
using a different model from the first review) and a from-scratch comparator re-run on a clean
checkout. Any disagreement, with
either Reviewer or with the earlier comparator result, pauses acceptance for that batch and is
escalated to the maintainer.

**Maintainer role.** The maintainer grants and edits gates in `docs/authorizations.md`, sets
budgets, decides licence and policy questions, and receives escalations and periodic summary
reports (counts accepted, rejected and escalated; spend). Escalate to the maintainer only for:
Reviewer `escalate` verdicts in the `provenance`, `legal` or `systemic` categories (`other` goes
to an Engineer and then a fresh Reviewer pass); systemic problems such as a comparator or
validator defect, a pass that fails to reproduce, or evidence that the accepted set contains bad
matches; new gates or spend beyond recorded limits; and changes to this acceptance rule.

**Audit and revocation.** The maintainer may audit any accepted function at any time and revoke
it. Revocation, or a failed re-run of an accepted function, sets its status back to `mapped` in
`data/progress.json` in a commit that adds a dated note to the function's finding stating the
reason; the earlier report stays in git history and is not cited as current evidence.
`tools/accept_function.py --revoke` makes the data change (status, `report`, review and match
records) and prints the note to add.

**Changes to the machinery.** Changes to the comparator, the validator's gate logic, verifier or this rule
are not covered by automated acceptance of functions. They need an Engineer change with tests and
a separate strong Reviewer pass on that change (Sol under `claude-low`, Opus otherwise,
independent of the Engineer), and are listed in the maintainer's summary report; they
are not blocked waiting for the maintainer, except changes to this rule itself, which escalate.

### Family reviews

A family identifies one generator or stamping template by version and template digest, bound to
the target build, recipe, compiler and comparator version. A change to any of these starts a new
family. Each member records its parameter row and target binding. Every member independently
passes the unchanged comparator on two independent approved hosts with different OS loaders,
against the integrated source and pinned recipe. All comparator, validator, provenance and
publication checks remain in force.

A fresh admitted Reviewer reviews the generator or template, parameter extraction and binding,
and the first 20 members. For every subsequent batch, record the seed and complete population
before selection, then draw a reproducible random sample of the greater of 20 or 5% of members,
rounding up; review all members if there are fewer than 20. The seed, complete population and
member bindings are committed before drawing, and the deterministic draw is committed before any
member is accepted. Review individually every member with parameters outside the reviewed ranges.
The existing sampling safeguard, including a second Opus
pass and a from-scratch comparator re-run for the first 20 per new Reviewer or rule version and at
least 5% random, applies to reviewed members with all its existing triggers. An unsampled member may
rely on the family only when its origin version and digest match a saved approving family review
under `.local/reviews/` by an admitted model, the family is active, and its parameters are in the
reviewed ranges. Every sampled member needs its own approval before the remaining batch is
accepted. Other functions retain the per-function rule. The sanitized member record names and
hashes the family review, family manifest and committed batch it relies on.

A comparator pass proves no name. Each function records its name source as a public symbol source
or a labelled guess, with its confidence. A family review does not substitute for the existing
provenance and publication requirements.

Pause the family on a Reviewer rejection of a sampled member, wrong parameter or target binding,
non-reproduction, provenance doubt, Reviewer disagreement or another material defect. Quarantine
affected members and assess the entire affected population. If a family is invalidated, revoke
any accepted member whose supporting evidence is invalidated; do not silently retain it. Correct
the cause and repeat the required comparisons and reviews before re-acceptance; escalate policy or
provenance uncertainty to the maintainer before resuming. A pause freezes new acceptance; it does
not silently revoke or endorse existing members. Revocation of invalidated evidence is explicit
and recorded under "Audit and revocation" above. Correct the cause and use a freshly reviewed
family version before resuming.

Family metadata, review format and commands are in `docs/reviewer-runbook.md` and
`docs/orchestrator-runbook.md`. `tools/family_review.py`, `tools/accept_function.py` and
`tools/flow.py` enforce the exemption; `tests/test_family_review.py` exercises it on synthetic
comparator reports. A schema 4 member approval is a family approval, never an individual review,
and cannot be carried forward by `--label-only`.

## Match gate

This is how `tools/check.py` enforces items 1 to 3 of tier 1 of the acceptance rule on the committed tree.
An inventory entry may name a match record in `report` (`reports/README.md`) before it is
accepted; that record is checked whenever it is named, so a record awaiting review cannot go
stale unnoticed. A `matched` entry must name one, and must also have a Reviewer record.

Match record, recomputed from the tree:

- **Source.** The record's `translation_unit` is exactly the include closure of its compiled
  file: every repository file reachable through quoted `#include "..."` directives,
  transitively, and nothing else. The scan keeps no lexical state: it does not try to tell
  comments or string literals from code, because approximating the C++ lexer is how earlier
  versions missed includes. Each file is decoded as strict UTF-8 with one leading BOM stripped,
  line endings are normalised and backslash-newline continuations spliced; then every logical
  line is examined wherever it sits (comment, string, `#if 0`):
  - a line that is exactly `#include "path"` or `#include <path>` (only spaces or tabs around
    the tokens, nothing after them) counts; a quoted one joins the closure even if it is
    commented out, which can only over-include, and an unresolvable one fails;
  - any other line holding both `#` and `include` or `import` is refused. This is a style
    constraint on reconstruction sources: never write `#` and `include` on one line in a
    comment or string (`// see #include order` is refused), and never put a comment or trailing
    text on an include line;
  - a line whose first non-blank character is `#` must name a directive from the allow-list
    `define`, `undef`, `if`, `ifdef`, `ifndef`, `elif`, `else`, `endif`, `pragma`, `error`,
    `line`; anything else (`# /**/ include`, a null `#`, `#warning`, `#import`,
    `#include_next`) is refused;
  - a line holding `#` and a universal character name (`\u`, `\U`) is refused.

  Refused anywhere in a file, raw or spliced: non-UTF-8 bytes; a backslash followed only by
  blanks at a line end; trigraphs `??=` and `??/`; the digraph `%:`; `include_alias`;
  `__has_include`; `_Pragma`; a raw string literal prefix (`R"`, `u8R"`, `LR"`, ...); `import`
  followed by `"` or `<` (header units). Why no quoted include that MSVC compiles can escape: a
  directive begins a logical line with `#`, possibly after whitespace or comments, and its name
  must be spelled out on that logical line, since continuations are spliced, macros cannot
  produce directives and the other spellings of `#` and of names are refused. So every real
  quoted include is on a line holding both `#` and `include`, which is either counted or
  refused. The argument is written out above `quoted_includes` in `tools/source_digest.py`.
  Recipe flags may name no include path or include behaviour other than `/I reconstruction`
  (also written `/Ireconstruction` or `-I`): `/I` or `-I` with any other directory, `/X`,
  `/FI`, `/FU`, `/AI`, `/Y*` (precompiled headers), `/external:*`, `/imsvc` and response files
  `@file` are refused, as is any argument that is not a flag. `/D` and `/U` are fine. The
  allowed directories are `INCLUDE_ROOTS` in `tools/source_digest.py`, the same constant the
  closure resolves against, so the check and the closure cannot drift (`recipe_flag_problem`,
  used by `tools/check.py` and `tools/verifier/tu_task.py`).

  A quoted include resolves against the including file's directory, then the directories of the
  files that included it (innermost first, as MSVC searches), then the include root
  `reconstruction/` (a source relying on it is compiled with `/I reconstruction`). It must
  resolve to exactly one regular file whose real path stays inside the repository and outside
  `.local/` and `.git/`, with no symlink in any path component, and spelled exactly as on disk
  with no sibling differing only in case (Windows hosts look names up case-insensitively);
  otherwise it fails closed as unresolvable or ambiguous. An angle-bracket include is resolved
  against the include root only (as MSVC searches `/I` directories, not the includer's): if it
  reaches a repository file it joins the closure exactly like a quoted include; if the name
  matches a repository path only case-insensitively or through a symlink, or contains `..`, it is
  refused; otherwise it is a toolchain or SDK header, bound by the pinned toolchain hash, not by
  the source digest. Directives inside `#if 0` are still counted, which can only over-include. The
  digest definition (`tu-sha256-v1`) is unchanged. The digest of that unit equals the record's, and every report
  names that digest and the compiled file's path. `tools/verifier/tu_task.py` applies the same
  closure rule, so a verifier task cannot be built from an incomplete unit.
  Build-path checks on the verifier host (`tools/verifier/unit_build.py`, used by
  `tools/verifier/attempt` and `tools/verifier/confirm`): the compile runs with `INCLUDE`, `LIB`,
  `LIBPATH`, `CL`, `_CL_` and `EXTERNAL_INCLUDE` removed from the environment; the msvc-wine
  wrapper then sets `INCLUDE` to toolchain and SDK directories, and the build fails if any entry
  lies outside the toolchain root. The value, the cleared names and the added flag are recorded
  in the private build record (`environment`). The compile adds `/showIncludes` to the recipe
  flags (measured once, on the first accepted unit: it changed no object section except the
  object-path record in `.debug$S` and its `.chks64` checksum; not re-measured per unit);
  every file the compiler opened must be under the toolchain root or a repository file, and the
  repository files must equal the include closure exactly, or the build is refused. A closure
  entry the compiler never opened (an include in a comment or dead `#if` branch) is a difference
  too; `tools/lint_reconstruction.py` refuses such includes earlier.
  These checks run on the verifier, not in `tools/check.py`: CI has no compiler. The match record
  carries each compile host's report of them in its `build` block (flags actually run, cleared
  variables, object hash, files opened) and its `reproduction` names the same command and
  environment; the gate requires that block and checks it for consistency with the runs and the
  unit, but cannot check that it is true, and the block says so.
  Follow-up, not implemented: the manual reproduction path (`tu_task.py` plus a hand-run `cl`)
  does not apply these checks; a third party reproducing by hand should clear the same variables.
- **Target.** Every report's image hash equals `builds/target.json`. Its build id, RVA and size
  equal the inventory entry's, and the current symbol map places the symbol at that range.
- **Recipe and compiler.** The recipe and `tools/verifier/pinned.sha256` match their recorded
  hashes. The recipe's compiler is the pinned `cl.exe`, and every report names that recipe's
  hash, compiler and flags.
- **Symbol map.** The record pins the SHA-256 of the map version its runs used. It binds if that
  is the current map, or if it is an earlier version all of whose entries are present and
  identical now and nothing added since could have changed the result. The first part is proven
  from content, not from history claims: `symbol-map.history.json` beside the map lists versions
  as name sets, and the gate rebuilds each version from the current map (same order, entries,
  fold groups and provenance entries, canonical JSON) and requires the rebuild to hash to the
  version's SHA-256; a version that does not rebuild fails the check unless the history marks it
  `superseded`, and a record pinned to a superseded or unlisted version is stale. The second part
  exists because a pass also depended on what the map lacked (`docs/comparator-contract.md`,
  "Aliases, folds and overlaps" and "Thread-local variables"): the record is stale if an added
  entry lies at or in the function range or is named as the function, `__ImageBase` or
  `_tls_index` was added, any thread-local entry was added (the comparator checks every
  thread-local entry against the image's TLS template, and the first one makes it require a TLS
  directory; reports carry no template bounds, so no record can show an entry its runs did not
  read to be harmless), an EH handler name was added and the function has handler data, or an
  added entry lies at or in a funclet range the runs' reports give (`coverage.funclet_ranges`;
  reports of a function with funclets whose ranges are not identical across runs, integer-counted,
  covering every compared funclet byte, and disjoint from each other and the function, in any
  order, carry across no addition). Names a pass referenced need no rule: the comparator fails a reference
  to a name its map lacks (`unresolved-symbol`), so a pass referenced none of the added names. Tests
  in `tests/test_symbol_map.py` fail if the comparator comes to name a symbol-like string literal
  or an entry kind without a rule here, if a function other than the audited ones in
  `docs/comparator-contract.md` ("Symbol map dependences") refers to map data by its names in
  `compare.py`, or if the comment- and docstring-free syntax tree of an audited function changes
  (with the `compare.py` functions they call by name, the `Function` methods they call on `self`
  and the module constants they use). They do not see a change in `pecoff.py`, a map read under
  another name, or an edit inside a helper reached any other way (`Function.helper(self, ...)`,
  or a method of another object), though adding such a call to an audited function changes its
  tree and fails them; passing them is not an audit, and a failure calls for one. Every run's report must name
  the pinned map in `symbol_map_sha256`, the comparator's hash of the bytes it read, so the pin
  cannot be moved without new runs. Changing or removing an entry
  therefore makes exactly the records pinned to versions holding it stale. The map is written
  only by `tools/symbol_map.py add` (bind uses it too): additions only, refusing changes,
  removals, entries sharing an address, TLS offset or range with an existing one, `__ImageBase`
  and `_tls_index` additions and anything that would make a valid record stale, unless
  `--allow-change` is given, which applies them, supersedes the
  affected versions and lists the records made stale. The map must be canonical JSON and may not
  repeat a key. `--history` imports a worktree branch's versions that still rebuild after the
  merge, so records confirmed on the branch survive integration.
- **Comparator.** Every report comes from the current comparator version and source hash and
  names the current contract version (`docs/comparator-contract.md`, version 2). A change to
  `tools/compare.py` or `tools/pecoff.py` therefore makes every record stale.
- **Result.** Every report has result `pass`, every function byte covered exactly or by
  reference, and unwind info `covered` or `none-in-range`. Under contract version 2 a `pass`
  also means that the exception-related scope the contract defines (handler data, funclets,
  chained unwind info, several `.pdata` entries per function, jump tables) was compared and
  fully covered; the contract, not this file, defines that scope and its unsupported cases.
  For funclets this includes their extent: each funclet is compared over the candidate's whole
  section, and the target must show that the funclet ends exactly there, by target-side evidence
  only: its own `.pdata` entry ending there; a `.pdata` entry starting there; compared code
  starting there; a funclet entry starting there that a FuncInfo reached through this function's
  own handlers names; or `int3` padding. No other function's funclet entry (under any handler)
  and no unchained `.pdata` entry of another procedure may lie inside it, and it may not run on
  past one of its own `.pdata` entries into code nothing starts. From comparator 0.6.0 the report
  names the evidence per funclet (`coverage.funclet_end_evidence`). Where the end is shown by a
  start that follows it or by padding (not by the funclet's own `.pdata` end), a pass may include
  trailing bytes that no metadata assigns to any procedure, lying before that next start; they
  are compared byte for byte, but metadata cannot say they belong to the funclet. The contract ("Exception and termination handlers")
  gives the rules, the premise they rest on and the cases that stay refused.
  Each report carries `candidate.code_section_sha256` over the function and funclet sections,
  which the gate requires from all runs or none, equal across runs (delta reviews below).
- **Reproduction.** There are at least two runs, from at least two compile hosts and two
  compare hosts. The record says how independent those hosts are. A machine booted from a disk
  fork (a copy) of another verifier machine counts as a different machine for acceptance: it
  compiles and compares in its own process, file system and object paths, which is what the
  second run checks. It shares the toolchain install and image, so it does not check those
  against an independent copy: the record labels such a pair with a note line starting
  `independence: fork` (otherwise `independence: separate-machine`, or
  `independence: third-party` for a host run by someone else). At least one accepted function
  per batch, or per day of acceptances if that is sooner, is also re-run on a machine that is not
  a fork of the compile hosts (a separately provisioned machine from the pinned recipe, or the
  macOS host for the comparison), and that re-check is recorded in the batch's handoff and in
  the summary report. An optional third-party host may be added later. The gate does not read the
  `independence` label yet; it is policy, checked by the sampling safeguard. Host names are
  self-reported labels: the gate cannot verify which machine produced a run. As a tripwire
  against one report copied under two labels, runs from different compile hosts must name
  different candidate object hashes (two clean compiles differ in time stamp and path records,
  so identical objects mean one compile was relabelled). A recipe that makes compiles
  bit-identical, such as `/Brepro`, would trip it and needs a gate change first.
- **Runner hosts.** Records may also come from the hosts named in the private runner config
  (`tools/verifier/runners.py`; the maintainer's own machines, `docs/authorizations.md` Notes).
  Such a record is evidence only if its compile hosts are at least two hosts from that config
  that are different physical machines (distinct `machine` in the config) and run the pinned
  compiler under different OS loaders (one natively on Windows, one under Wine on another OS),
  each with its own install of the toolchain and its own copy of the image, both hashed during
  the confirm run before compiling (no cached check). Every compile host compares its own
  object, and the `local` host, which must be one of the compile hosts, also compares every
  other host's object. The record carries a note starting
  `independence: separate-machine, different-loader` that names each compile host by its host
  id, machine, OS, CPU architecture, loader and the SHA-256 of the compiler binaries it ran.
  `tools/verifier/confirm` refuses to write a record unless the config names two machines, the
  hosts' own reports show two loaders and two operating systems, a host reporting `native`
  reports Windows, each host reports the loader its config names and a fresh toolchain check,
  and a `local` host is among the compile hosts. Such a pair is not a fork of each other, so a
  record from it also satisfies the per-batch re-check above. Every other condition of this
  section is unchanged. Machines and loaders are self-reported like all host labels; the OS
  check makes "one natively on Windows" a measured claim only to the extent the host's own
  Python reports its platform truthfully.
- **Combining hosts.** All compile hosts of one record are of one kind: either all are Boat
  machines meeting "Reproduction" above, or all are runner hosts meeting "Runner hosts". A
  record whose compile hosts mix the two kinds is not evidence under either bullet;
  `tools/verifier/confirm` never writes one (runner confirm lists runner hosts only).

Reviewer record, `reports/<build id>/<rva>.review.json` (RVA as in the inventory id), for every
`matched` entry:

- exactly the fields `review_record_schema`, `function_id`, `build_id`, `rva`, `size`,
  `source_digest_method`, `source_digest`, `reviewer_model`, `review_task_id`, `verdict`,
  `escalation_category`, `review_sha256` and `review_date` (schema 1), plus `review_kind`,
  `previous_source_digest`, `previous_review_sha256`, `previous_code_section_sha256` and
  `code_section_sha256` (schema 2), plus `naming_findings` (schema 3, written by
  `tools/accept_function.py`), plus structured `family_evidence` for schema 4 family approvals
  (`reports/README.md`), so the only free text published is the naming findings;
- a record below schema 3 is accepted only if its path and the SHA-256 of its canonical JSON are
  listed in `tools/legacy_review_records.json`, generated from the 58 records that existed at
  commit `e51d00a` when the four-check review format took effect. A list outside the records is
  used rather than a date bound because `review_date` sits in the record itself, so a hand-written
  record could carry any date; an edited or new legacy record needs an edit to that tracked file;
- schema 2 and 3: a `full` review has no previous fields and its `code_section_sha256` equals the
  match record's (or both are absent); a `delta` review names a previous digest other than its
  own, a previous review hash, and a previous code-section hash equal to its own and to the
  match record's (next section); a `label-only` record (schema 3 only) is a `delta` whose
  previous review hash equals its own review hash, since no new review was made, and whose
  code-section hashes are present;
- schema 4: only `review_kind: family`, with no previous fields and the current code-section
  hash, a matching pinned family spec and saved approval hash, a committed batch whose sample
  recomputes from seed and population, the exact member digest and parameters inside reviewed
  ranges, and membership outside that sample. The acceptance tool additionally checks the actual
  private approval, admitted model, active family, git ordering and individual sample reviews
  with their safeguards;
- schema 3: `naming_findings` is a list of at most 20 single-line strings of at most 300
  printable ASCII characters, none holding a brace, a backtick fence, a private path (`.local`,
  `/Users/`, `/home/`, `~/`, a drive letter), a run of 16 or more hex digits, four or more
  space-, comma-, semicolon-, colon- or dash-separated hex byte pairs, a run of 10 or more hex
  digits mixing digits and letters (unless right after `@`, a commit pin), four or more two-digit
  `0x` values in a row (unless fewer than eight and strictly ascending, as field offsets are), two
  or more `\x`-escaped bytes, a bracketed register operand or a `ptr` operand; a `full` or `delta`
  record has a list, a `label-only` record a
  list or `null` (carried from a record that predates the field). The filter is mechanical; the
  Reviewer writing them is responsible for the rest of their hygiene;
- the function identity equals the inventory entry's, and the source digest equals the match
  record's, so an approval cannot be reused for other source or another function, and a change
  to any file in the compiled file's include closure (above) makes it stale together with the
  match record;
- a reviewer model is named, the verdict is `approve` with escalation category `none`, the review
  hash is a SHA-256 and the date is a valid ISO date;
- a Reviewer record for an entry that is not `matched` is rejected, so a leftover approval never
  reads as acceptance.

## Stale acceptances and delta reviews

A `matched` entry stays bound to the exact unit digest, so adding a function to a unit, or any
other edit to a file in its include closure, makes its acceptance stale. `tools/check.py` reports
every such entry by name, with its record and unit, as `Stale acceptance (unit changed)` (the
match record no longer binds the integrated source) or `Stale acceptance (review behind)` (the
record was regenerated but the Reviewer record binds the earlier digest), and fails until it is
cleared; CI and the pre-commit check are blocked meanwhile. The inventory status stays `matched`
during that window (no revoke), and `reconstruction/INDEX.md` shows `STALE`. Clearing it:

1. Re-confirm: `tools/verifier/confirm` regenerates the unit's match records by real runs on two
   hosts, as for a new function. Until then nothing else can proceed. `confirm` runs on the
   working tree, because the pre-commit check blocks a commit that holds the unit change alone:
   the unit change, its new records, the re-review and the acceptance land in one commit. Each
   record notes the base commit and the inputs that were uncommitted when it ran; what it binds
   is the unit digest, recipe and map hashes, which the check recomputes from the committed tree.
2. Re-review: a Reviewer approves the function again, either by a full review or by a delta
   review, or, when the compared code section is unchanged, the tool re-accepts it without one
   ("Label-only re-acceptance" below). A delta review reads only the unit diff from the digest the earlier approve bound to
   the new one (`tools/review_packet.py` prints it, from the commit where that digest was
   current) and needs the compared code section hash (`candidate.code_section_sha256`,
   `reports/README.md`) to be the same in the approved record and the new one: the function's
   own compiled code did not change, so only what the diff shows (renames, labels, stand-ins,
   comments, new code) is new to review. If the hash changed, is missing from either record, or
   no earlier approve of that digest is found, only a full review is accepted.
3. Accept: `tools/accept_function.py` (`--all-approved` for a batch) checks the review block
   (`review_kind: delta`, `previous_source_digest`, `code_section_unchanged: yes`), that the
   superseded Reviewer record approved exactly `previous_source_digest`, and that the previous
   code-section hash (from that record, or from the match record at the commit where the digest
   was current) equals the new one; then it replaces the Reviewer record with a schema 3 record
   binding both digests and both hashes.

A delta review is not weaker evidence of a match (the reproduced comparator pass is the
evidence and is re-run in step 1); it narrows what the Reviewer re-reads to what changed. Records
written before comparator version 2 carry no code-section hash; a stale acceptance whose
approved record lacks it needs a full re-review.

### Label-only re-acceptance

This path extends individual approvals only. A schema 4 family approval needs a full individual
review or a newly committed eligible family batch; it cannot become a label-only record.

Step 2 needs no Reviewer when the function's compared code did not change: then the code a
Reviewer approved is the code the new runs compared. `python3 tools/accept_function.py
--label-only [--functions ...] [--units ...]` re-accepts such an entry. Its scope is wider than
"a label change": it re-accepts **any** change to the unit that leaves the function's code-section
hash the same on both compile hosts. That includes comments and labels, renames that do not change
the name of a relocation target, data definitions and stand-in bodies, the text of other functions
of the unit, functions added to the unit, and the function's own text rewritten into a form that
compiles to the same code. Other functions of the unit are outside this function's claim (each has
its own acceptance); they are not naming material of this one. Diff confinement is not
proven and not needed for the match claim: the evidence is the code-section hash, which covers every code byte, every
relocation's offset and type and its target symbol's name, so renaming a callee or a referenced
global changes it and needs a review. For each selected entry the tool requires, and refuses the
whole run otherwise:

1. the entry is `matched` and its state is `review behind`: the match record binds the
   integrated unit digest (re-confirmed, step 1) and the Reviewer record an earlier one;
2. the match record passes the whole match gate (two compile hosts, two compare hosts, current
   comparator and pins, full coverage, and so on);
3. every run of the record gives `candidate.code_section_sha256` and they agree, which includes
   both compile hosts (`record_code_section`);
4. the superseded Reviewer record is an `approve` with escalation `none` for this function, of a
   known schema, binding another digest than the current one;
5. the code-section hash that approval covered (from the superseded record, or from the match
   record at the commit where its digest was current) exists and equals the new one;
6. `tools/lint_reconstruction.py` reports nothing for the unit's files.

It then writes a schema 3 record with `review_kind: label-only` that binds the new digest and the
code-section hash and carries forward the superseded record's `reviewer_model`,
`review_task_id`, `review_sha256`, `review_date` and `naming_findings`
(`previous_review_sha256` equals `review_sha256`), and recomputes `named`. Repeated label-only
steps chain: each needs the hash equal to its predecessor's, so all equal the hash the last
Reviewer approved. Carried findings stay open until a Reviewer closes them (tier 2); a full review
may replace a `label-only` record of a current entry for that purpose.

What `tools/check.py` checks for a `label-only` record, from the tree alone: the delta checks
above (previous digest a SHA-256 other than the current, code-section hashes present and equal to
the match record's), previous review hash equal to the review hash, and the naming-findings
filter. Items 4 and 5 compare against the superseded record or git history, which the validator
does not read; as for delta records, a hand-written record claiming them is caught only by git
history and the sampling safeguard. What this gives up: a Reviewer no longer reads a source change
that leaves the function's compiled code identical, so a rewrite of the function's own text into
something a Reviewer would reject (pasted decompiler output that compiles to the same code) is
not re-checked until the next full review or the sampling safeguard, which samples label-only
acceptances like any other. Nor is any other unit text on this path: comments, labels, other
functions' bodies and added code are published without a Reviewer reading them, until a later
review of some function of that unit. This is not a new publication channel, since unaccepted
drafts are committed unreviewed too, but no Reviewer has vouched for that text.

### Re-review with an earlier review as context

A review written before the current output format (no `report_binding`, `checks`,
`blocking_findings` or `naming_findings`) is refused by the acceptance tool, and its verdicts are
never converted by script: an earlier `reject` may rest on a reason that is now a naming finding,
or on a blocking one, and only a Reviewer can tell which. Such functions get a new full review
in the current format, which may start from the earlier one:

    python3 tools/review_packet.py --prior-review .local/reviews/<earlier>.md [--prior-ref <commit>] [ids...]

Without ids the packet covers every function the earlier review has a block for, except those
already accepted at the current digest. Per function it prints the earlier block verbatim, the
earlier file's SHA-256 and the digest it reviewed, whether the unit still has that digest, and if
not the unit diff from a commit where it had (found in history, or `--prior-ref`, whose digest
is checked first; no diff without a verified base), the FNV counterparts from the sibling index,
and a blank block in the current format with a `prior_review: <task-id> <sha256>` line. The
Reviewer re-judges every earlier reason against the blocking grounds, moves naming ones to
`naming_findings`, and still checks the whole function: the earlier review saves reading time,
it is not evidence, and `prior_review` is ignored by the acceptance tool. When the digest is
unchanged and the earlier rejects were naming-only, the new review is mostly a reclassification;
when the unit changed with no verified base, the Reviewer reads the whole unit.

### Temporary holds

One operational hold applies on top of the rule above. It is temporary: it lifts when its
condition is met, and the tools already enforce the rule itself. (The earlier hold that confined
`--label-only` to label-and-comment diffs lifted when the maintainer confirmed the wide scope,
`docs/authorizations.md` Note.)

- Until the extract path refuses stray review blocks in a transcript, accept reviews only from
  files saved under `.local/reviews/`, never with `--review -` (stdin) or a path outside the
  repository. Why: text cut from a transcript can carry a block that was never the final verdict.

## Acceptance tool, source lint and tests

`tools/accept_function.py` checks the private review file (its block for the function says
`approve`, no escalation, fresh context, not drafted or triaged by the Reviewer, a model, and the
match record's source digest) before writing the Reviewer record, then re-runs the validator and
changes nothing if it fails. The validator cannot see the private review, so the record's hash is
what ties it to the file kept under `.local/reviews/`. With `--all-approved` it accepts every
`approve` block of one review in one all-or-nothing step; the review may come from stdin or a
transcript outside the repository, and is then saved to `.local/reviews/<task-id>.md` first. It
also refreshes `updated_at` and `reconstruction/INDEX.md` and prints the files to stage.
An `approve` block must also give `report_binding: agree`, `pass` for the four blocking checks
(`plausible_source`, `provenance`, `claim_scope`, `publication_hygiene`), `blocking_findings:
none` and a `naming_findings` field (`none` or a list), or it is refused as inconsistent.
The saved review group's profile governs admission even if the active session later changes.
A caller-supplied `--profile` must agree with that group, or with the active session when no
group records the task; with neither, only the configured default is allowed. Start a session
before first use of another profile. `SKYRIM_FLOW_DIR` is accepted only when it resolves to
`.local/flow` under the shared checkout (the parent of the git common directory), including
isolated integration worktrees. Saved groups, session events and independence assertions remain
local, unauthenticated state: these checks prevent mistakes, not deliberate state forgery.
The block parser fails closed. The saved review must start at its `# Review <task-id>` title,
hold no second title (in any case, in any section) and no unseen characters (control or format
characters other than tab and CRLF, line separators, spaces other than U+0020). A section is a
function block if its heading's first word is an inventory build id in any case, or if any of its
lines starts with "verdict"; its heading must then be exactly `<build id> 0x<lowercase hex RVA>
<size>` for an inventory function and that function's size, so a reject block with a heading such
as `0x1010:` or an upper-case build id refuses the review instead of being dropped. In the header
and in every function block (accepted or not) the parser refuses unknown keys, a key, check or
list item given twice, a line that is not a field, a check sub-line, a `- ` item or a continuation
(of `reasons`, or of an item indented at least to the item's text), items of one list at different
indents, a list field with any value other than the literal `none` or with an empty value and no
items, a closed-word field (verdict, escalation category, review kind, yes/no fields, report
binding, the four checks) with another word or spelling, a block without all four checks, and a
block missing any of its fields through `reasons`. The full grammar, and a mutation test that
changes every structural token of a valid review one at a time, are in
`tests/test_review_mutations.py`. A review refused for its format is remedied by a new Reviewer
run under a new task id, never by editing the saved review: the saved file is what the record's
hash binds, and an edit by anyone but the Reviewer would make the record vouch for text no
Reviewer wrote.
`--functions` (inventory ids or `0x<rva>`) and `--units` (compiled file, or `<area>/<Class>`)
restrict `--all-approved`, `--label-only` and `--refresh-named` to a subset; a selected function
without an `approve` block is refused. Entries outside the selection that were already stale
before the run may stay stale; the selected ones, and every other entry, must validate.

Source lint: `tools/check.py` also runs `tools/lint_reconstruction.py` on every file under
`reconstruction/` (tracked or new; the index tree with `--staged`). It checks the mechanical part
of the Reviewer's list: no inline assembly, `__emit`, raw byte arrays or `\x` byte strings,
universal character names (`\u`, `\U`) anywhere, pragma operators, codegen-only `#pragma` or
`__declspec`; a justification comment beside `__forceinline`, `noinline`, `[[msvc::...]]` and
codegen intrinsics; GPL (any case) named in the leading comment of a file with a GPL-licensed
`COMMUNITY` label, every `COMMUNITY(` (any case) written as a well-formed label, and the listed
spelling and licence word on any label for a known community repository, compared without case
(`COMMUNITY_LICENCES`); every MIT licence notice in a comment complete (copyright line, then
the permission and disclaimer text matching a stored hash, and the cited repository's whole
LICENSE where its pinned clone is under `.local/sources/`); the name-origin label grammar in files that declare `Labels: v2`;
`SIBLING(...)` labels in every file and `Sibling source:` lines limited to an allowed sibling at
its pin, the latter with no `..` path component; the header comment fields of
`reconstruction/README.md`; the one-class-per-pair layout; and include style (quoted repository
headers, no include in a block comment or conditional block, every include name a plain relative
path with no drive letter, backslash, leading `/` or `..`, so contributed source cannot make the
compiler open a host file before the verifier's include check). Passing the lint does not replace
the Reviewer; it only spares the Reviewer those checks. Tests: `tests/test_lint_reconstruction.py`.

The negative tests in `tests/test_match_gate.py` reject each of these when it is missing,
stale or inconsistent, `tests/test_accept_function.py` covers the acceptance tool, and `tests/test_acceptance_flow.py`
covers stale acceptances, delta reviews, batch acceptance and the generated index, and
`tests/test_two_tier.py` covers the blocking grounds, naming findings, tier 2, subset selection
and label-only re-acceptance, and `tests/test_merged_rules.py` probes the two-tier rule together
with the sibling source (lint, label check against a synthetic clone, sibling-label naming
findings, undeclared reuse blocking) and the packet's re-review options,
`tests/test_review_parser.py` and `tests/test_review_mutations.py` cover the fail-closed review parser, the naming-findings filter
and the legacy-record list, and `tests/test_lint_hardening.py` the licence table, sibling
citations in every file, `..` paths and the label check's template parsing. They use
reports that the comparator produced from synthetic fixtures. The comparator itself is tested
in `tests/test_compare.py` against its contract (`docs/comparator-contract.md`).

What the gate can and cannot show: it checks that public files agree with each other (source,
recipe, pins, reports, Reviewer record). Host identity in the runs and the whole Reviewer record
are self-reported by whoever wrote them; nothing in the tree authenticates them. The gate
therefore cannot show that a comparison against the game took place, that it ran on the hosts
named, or that a Reviewer read the source. Those rest on the runs and the review being real. The
safeguards for that are the sampling safeguard above (a second independent Reviewer pass and a
from-scratch comparator re-run for a sample of accepted functions) and git history as the audit
trail, not the validator. Likewise no tool can tell a naming finding from a misfiled blocking
ground: an `approve` that lists, say, "the body is pasted decompiler output" under
`naming_findings` passes every mechanical check and is accepted. Only the sampling safeguard's
second Reviewer pass can catch that misclassification.

Public CI cannot prove a match without private game inputs. It should check report/source
consistency, not represent that check as an independent comparison to Skyrim. Once an authorized
private worker exists, define credential isolation and publish only reviewed metadata. Never run
untrusted PR code on a self-hosted machine that has private game inputs or account credentials.

## Behavior and names

Behavior claims require controlled original-game observations, test conditions and alternative
explanations. Header declarations, AI comments and similar FNV code (usable as source by the
maintainer's decision) can suggest hypotheses but cannot establish Skyrim behavior. Separate measured observations from inferred algorithms.

## Progress and history

The page renders the current committed data and source revision. Work items use `planned`,
`active`, `blocked`, `done`. Milestones identify actual dated outcomes. No simulated trend,
leaderboard, cost ledger or percentage is displayed without real supporting records.
Add those only when there is data and a reviewed metric definition. Every record has an owner
and outcome criteria. Update `updated_at` when the data changes. Git history is the audit trail.
